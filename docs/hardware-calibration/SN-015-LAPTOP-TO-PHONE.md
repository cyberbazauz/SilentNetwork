# SN-015 — LAPTOP → PHONE: ручной акустический тест

**Задача:** SN-015, Windows Desktop Acoustic Lab + Android Audio Lab Receiver  
**Ветка:** `agent1/m0-acoustic-lab` (merge `aba35cc`)  
**Статус кода:** готов; Windows и Android объединены, синтетические тесты проходят  
**Статус доставки:** APK — `dist/SilentNetwork-Android.apk`; Windows — `dist/SilentNetwork-Desktop/`  
**Статус физического воспроизведения:** `PENDING`  
**Статус теста LAPTOP → PHONE:** `PENDING`  
**Порядок первого запуска:** `docs/hardware-calibration/SN-015-FINAL-DELIVERY.md`  
**Дата документа:** 2026-11-02

> Этот документ описывает **ручной** сценарий. Приложение не управляет
> телефоном по сети, не использует Wi-Fi, Bluetooth или сотовую связь как
> транспорт данных. Звук идёт только через динамик ноутбука и микрофон
> телефона. Ни один пункт ниже не считается выполненным, пока не получен
> реальный WAV с телефона и реальный playback JSON.

## 0. Что проверяется и что не проверяется

Проверяется только физическая передача одиночного тона:

```text
Windows PC → выбранный динамик → воздух → микрофон Android → WAV → анализ
```

Не проверяются и не заявляются:

- передача данных, BER, PER и работа модема;
- дальность 50–100 м;
- «неслышимость» и ультразвуковая приватность;
- универсальная совместимость Android-устройств;
- калибровка АЧХ всего тракта по одному файлу;
- SNR одиночной записи: эталонного сигнала нет, поэтому в отчёте `SNR = N/A`;
- автоматический PASS только потому, что обнаруженная частота близка к
  ожидаемой.

## 1. Запуск приложения

Из каталога `acoustic-lab`:

```powershell
python -m pip install -r requirements.txt
python desktop_app.py
```

Или двойным щелчком по `run_desktop.bat`.

При запуске приложение автоматически выбирает системный динамик:

- PLAY доступен после создания сигнала и требует подтверждения;
- аудиопоток открывается только на время воспроизведения;
- список устройств можно обновить и выбрать другой динамик вручную;
- флаг `--hardware-test` оставлен для совместимости и не блокирует PLAY.

Проверка сборки GUI без звука:

```powershell
python desktop_app.py --smoke-test
```

Ожидаемая строка:

```text
GUI smoke test OK: hardware_test=False, play_enabled=False, ...
```

`play_enabled=False` ожидаемо: сигнал ещё не создан.

Если Python установлен из Microsoft Store и Tk не находит `tcl8.6`/`tk8.6`,
приложение пытается подставить `TCL_LIBRARY` и `TK_LIBRARY` из
`sys.base_prefix\tcl`. Это исправляет ошибку `ttk/fonts.tcl`, но не заменяет
полноценную установку Python с Tcl/Tk.

## 2. Выбор динамика ноутбука

1. Открыть секцию **A. OUTPUT DEVICE**.
2. Нажать **«Обновить устройства»**. Это только перечисление, поток не
   открывается.
3. Найти вручную динамик ноутбука, например
   `Speaker (Realtek(R) Audio)` / `MME`.
4. Выделить строку. Приложение не выбирает default output и не подставляет
   Bluetooth/виртуальные устройства.
5. Нажать **«Проверить 48/44.1 кГц»**. Это вызов
   `check_output_settings`, поток не открывается.
6. Если 48 000 Гц отклонена драйвером, выбрать 44 100 Гц. Скрытого
   ресемплирования нет: при отказе будет ошибка.

Записать в отчёт: индекс устройства, имя, Host API, поддержку 48/44.1 кГц.

## 3. Первый WAV без звука

В секции **B. TEST SIGNAL GENERATOR**:

| Параметр | Значение |
|---|---|
| Частота | `1000` Гц |
| Sample rate | `48000` Гц |
| Длительность | `3.0` с |
| Амплитуда | `0.10` |
| Тишина до | `500` мс |
| Тишина после | `500` мс |

Нажать **«Создать WAV (без звука)»**. Приложение создаёт в
`acoustic-lab/results/hardware_calibration/`:

- `tone-1000Hz-48000Hz-<timestamp>.wav` — PCM16 mono;
- `tone-1000Hz-48000Hz-<timestamp>.json` — параметры, SHA-256, окружение,
  `playback.performed = false`.

Проверить в JSON:

- `tone.frequency_hz = 1000.0`;
- `tone.pcm_format = pcm_s16le`;
- `file.channels = 1`;
- `file.sha256` совпадает с файлом;
- `playback.status = "not_requested"`.

**На этом шаге звук ещё не воспроизводился.** Наличие WAV не доказывает
работу динамика.

## 4. Подготовка Android

1. Установить на телефон приложение для записи WAV без сжатия.
2. Выбрать PCM/WAV, mono, 44 100 или 48 000 Гц, без AGC и шумоподавления,
   если приложение это позволяет.
3. Отключить системные «улучшения звука», если они доступны.
4. Включить авиарежим, чтобы уведомления не создавали лишний шум.
5. Положить телефон на расстоянии, указанное в протоколе измерения
   (например, 30 см), динамиком к ноутбуку.
6. Начать запись длительностью **10 секунд**.
7. Только после начала записи переходить к шагу 5.

Управление телефоном из Windows отсутствует: синхронизация выполняется
вручную по времени.

## 5. Ручное воспроизведение

PLAY доступен при обычном запуске:

```powershell
python desktop_app.py
```

или

```powershell
run_desktop.bat
```

Флаг `--hardware-test` сохранён для совместимости и даёт то же поведение.

Порядок:

1. Убедиться, что телефон уже пишет.
2. Проверить автоматически выбранный динамик или выбрать другой вручную.
3. Создать WAV для 1 000 Гц.
4. Нажать **PLAY**.
5. Подтвердить диалог: приложение показывает частоту, длительность,
   амплитуду, устройство и Host API.
6. Ноутбук воспроизводит 3 секунды тона.
7. Дождаться сообщения `PLAY завершён` и появления
   `*.playback-<timestamp>.json`.
8. Нажать **STOP** только если нужно прервать тест. STOP помечает
   воспроизведение как неполное; JSON всё равно создаётся, но
   `performed = false`.

В playback JSON фиксируются:

- timestamp начала и окончания;
- частота, sample rate, длительность, амплитуда;
- индекс устройства, имя, Host API;
- PCM format;
- SHA-256 WAV;
- статус `completed` / `stopped` / `failed`;
- `frames_written`, `frames_total`, `elapsed_s`;
- фактическая ошибка драйвера, если она была.

JSON создаётся только после реально завершённой попытки PLAY. Отмена
подтверждения не создаёт JSON.

## 6. Импорт WAV с телефона

1. Остановить запись на телефоне.
2. Экспортировать WAV без сжатия.
3. Передать файл на Windows любым файловым способом (кабель, файловый
   менеджер). Это не сетевой транспорт данных SilentNetwork.
4. В секции **D. PHONE WAV → ANALYSIS** указать
   **Expected frequency = 1000**.
5. Нажать **«Импорт WAV с телефона»** и выбрать файл.

Приложение:

- копирует оригинал в `results/hardware_calibration/imported-*.wav`;
- не изменяет исходный файл;
- считает SHA-256;
- создаёт `*.analysis.json`, `*.analysis.csv`, `*.psd.png`,
  `*.spectrogram.png`.

Поддерживается только PCM16 WAV с 1–8 каналами. Пустой, обрезанный или
повреждённый файл отвергается с ошибкой формата.

## 7. Анализ

В окне и в JSON отображаются:

| Показатель | Что означает |
|---|---|
| Duration | длительность записи телефона |
| Sample rate | фактический Fs файла |
| Frames | число отсчётов |
| RMS dBFS | средний уровень |
| Peak dBFS | максимальный уровень |
| Crest factor | peak − RMS |
| DC offset | постоянная составляющая |
| Clipping | отсчёты, упёршиеся в предел шкалы |
| Global dominant peak | самый заметный пик во всём спектре |
| Expected frequency | частота, которую передавали |
| Detected frequency | пик в окне ±300 Гц вокруг ожидаемой |
| Offset | Detected − Expected |
| Detection margin | превышение пика над медианой окна |
| Band 18–19 kHz | интегральная энергия полосы 18–19 кГц |
| SNR | `N/A`, потому что нет эталона |

Метод: Welch PSD, Hann, поиск максимума в окне ±300 Гц, уточнение
параболической интерполяцией по трём бинам. Пик учитывается, только если он
выше медианы окна не менее чем на 6 дБ.

**Близость частоты сама по себе не является PASS.** Нужно учитывать уровень,
клиппинг, ширину пика, спектрограмму и повторяемость.

## 9. Последовательность измерений

Начинать **строго с 1 кГц**. Не переходить к ультразвуку, пока не получен
валидный результат на 1 кГц.

Для каждой частоты:

1. Создать WAV с параметрами: Fs 48 000 Гц, 3 с, амплитуда 0.10,
   тишина 500 мс до/после.
2. Начать запись телефона на 10 с.
3. Выполнить PLAY и подтвердить.
4. Дождаться `completed`.
5. Остановить запись, экспортировать WAV.
6. Импортировать WAV с Expected frequency, равной переданной частоте.
7. Сохранить JSON/CSV/PNG.
8. Повторить измерение **три раза** для оценки повторяемости.

Порядок частот:

| № | Частота, Гц | Примечание |
|---:|---:|---|
| 1 | 1 000 | обязательный первый тест |
| 2 | 3 000 | речь/музыкальный диапазон |
| 3 | 5 000 | верхняя речевая область |
| 4 | 8 000 | широкополосный динамик |
| 5 | 15 000 | начало ВЧ |
| 6 | 17 000 | граница слышимого |
| 7 | 18 000 | экспериментальный диапазон |
| 8 | 18 500 | экспериментальный диапазон |
| 9 | 19 000 | экспериментальный диапазон |

Дополнительно, если предыдущие точки прошли: 10, 12, 16, 20, 21, 22 кГц.
При Fs 44 100 Гц частота 22 000 Гц ниже Найквиста (22 050 Гц), но
аппаратная поддержка не гарантируется.

## 10. Критерии PASS / FAIL

Пороговые значения ниже — **предлагаемые критерии приёмки**, а не
подтверждённые характеристики оборудования. Product Owner утверждает их до
начала физических измерений.

### PASS для одной частоты

PASS ставится только если выполнены **все** условия:

1. WAV создан, SHA-256 совпадает, формат PCM16 mono.
2. PLAY существует в JSON со статусом `completed` и `performed = true`.
3. Телефонная запись импортирована без ошибки формата.
4. Клиппинг отсутствует: `clipping.detected = false`.
5. Expected frequency и Detected frequency различаются не более чем на
   `max(3 Гц, один бин PSD)` для частот до 5 кГц, не более чем на 10 Гц для
   5–15 кГц и не более чем на 20 Гц для 16–22 кГц.
6. Detection margin ≥ 10 дБ над медианой окна ±300 Гц.
7. Пик виден на PSD и на спектрограмме как устойчивая горизонтальная линия
   длительностью не менее 1 с.
8. Три повторных измерения дают Detected frequency в пределах допуска из
   п. 5 и уровень в пределах ±6 дБ.
9. Уровень тона выше уровня соседних полос не менее чем на 10 дБ.
10. В отчёте явно указано, что SNR = `N/A`, а результат относится только к
    данной паре «ноутбук + телефон + расстояние + помещение».

### FAIL

FAIL ставится, если:

- PLAY не выполнялся, был отменён, прерван STOP или завершился ошибкой;
- телефонный WAV не читается, пустой, обрезанный или не PCM16;
- обнаружен клиппинг, который нельзя устранить снижением амплитуды;
- устойчивый пик на ожидаемой частоте не найден;
- Detected frequency выходит за допуск, а повторный тест это подтверждает;
- результат не воспроизводится в трёх попытках;
- уровень тона неотличим от соседних полос.

### INCONCLUSIVE

Результат `INCONCLUSIVE`, если запись сделана, но:

- телефон применил неизвестное шумоподавление/AGC;
- запись слишком коротка;
- уровень фона менялся во время теста;
- частота попала в область, где PSD телефона обрезан или содержит
  собственный фильтр;
- нет трёх повторностей.

`INCONCLUSIVE` нельзя переводить в PASS без дополнительного измерения.

## 12. Известные ограничения

- Физическое воспроизведение ещё не выполнялось.
- Реальная запись Android ещё не получена; импорт проверен только
  синтетикой.
- Windows может применять AGC, шумоподавление и ресемплирование.
- Android почти всегда применяет собственную обработку звука; её параметры
  неизвестны.
- Микрофон ноутбука ранее показывал очень низкий уровень; для телефона
  уровень будет другим.
- Частоты 18–22 кГц могут отсутствовать в тракте или быть подавлены
  фильтром телефона.
- Один WAV не позволяет отделить шум от сигнала и вычислить SNR.
- Наличие пика не доказывает поддержку частоты для передачи данных: для
  этого нужны BER/PER тесты модема.

## 13. Что докладывать Product Owner

После каждого физического прогона приложить:

1. Список выполненных частот и число повторностей.
2. Сводную таблицу Expected / Detected / Offset / Margin / уровень.
3. Ссылки на JSON, CSV и PNG.
4. Явное указание, какие тесты были физическими, а какие — файловыми.
5. Вердикты PASS / FAIL / INCONCLUSIVE по каждой частоте.
6. Причину любого `FAIL` и `INCONCLUSIVE`.

До получения этих данных общий статус остаётся:

```text
SN-015 DESKTOP APP CODE — DONE (tests only)
PHYSICAL PLAYBACK — PENDING
LAPTOP → PHONE TEST — PENDING
```
