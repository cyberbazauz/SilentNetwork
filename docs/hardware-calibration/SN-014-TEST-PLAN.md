## 0. Назначение и границы

Документ описывает 11 шагов проверки реального тракта
**динамик → воздух → микрофон** на одной машине с Windows, с помощью
инструментов SN-014:

| Инструмент | Роль | Открывает устройства |
|---|---|---|
| `acoustic-lab/tonegen.py` | создать тестовый WAV и JSON-план | **нет, никогда** |
| `acoustic-lab/analyze.py` | посчитать метрики готового WAV | **нет, никогда** |
| `acoustic-lab/response.py` | сравнить TX и RX WAV | **нет, никогда** |
| `acoustic-lab/calibrate.py` | тон-сетка через динамик и запись микрофоном | только с `--hardware-test` |
| `acoustic-lab/scanner.py` | устройства, форматы, фоновая запись | только с `--capture` |

**Что план может доказать:** проходит ли конкретная тон-сетка от выбранного
динамика к выбранному микрофону при текущих настройках Windows, с каким
уровнем, SNR и смещением частоты.

**Что план не доказывает:** передачу данных, BER, дальность, неслышимость,
работу на другом оборудовании, работу Windows ↔ Windows и пригодность
BFSK/CPFSK. Успешный `PASS` здесь означает только «тоны обнаружены в записи».

## 1. Безопасность и запреты

1. Все команды без `--hardware-test` **обязаны** работать без звука. Если
   инструмент без флага начал воспроизведение или запись — это дефект, тест
   прекращается.
2. `--hardware-test` разрешает физический тест: динамик воспроизведёт тоны, а
   микрофон будет записывать. Запускать только осознанно.
3. 18–19 кГц не слышны большинству взрослых, но могут быть слышны детям и
   животным. Начинать с умеренной громкости Windows (30–50 %), не надевать
   наушники, не направлять динамик вплотную к уху.
4. Не запускать два физических теста одновременно и не оставлять фоновых
   процессов с аудиопотоками.
5. WAV, PNG, CSV и JSON экспериментов **не коммитить**. В Git попадают только
   `results/*.md` и код.
6. Запрещено подбирать `--min-snr-db` и `--max-offset-hz` после просмотра
   результата: пороги фиксируются до прогона (по умолчанию 10 дБ и 50 Гц).
7. Запрещено выдавать результат одного прогона за характеристику оборудования
   вообще. В отчёт попадают устройство, host API, настройки, время и файл.

```powershell
python calibrate.py --hardware-test --frequencies 1000,2000,4000,8000 --required 1000,2000,4000,8000 --tone-ms 500 --gap-ms 300 --lead-ms 500 --tail-ms 500 --amplitude 0.3 --output-device <OUTPUT_INDEX> --input-device <INPUT_INDEX> --out results\sn014\control.wav --report results\sn014\control.json --plot results\sn014\control.png
```

Ожидаемая длительность — 3.9 с. Перед запуском убедиться, что звук уместен.

**Ожидаемо:** предупреждение `ФИЗИЧЕСКИЙ ТЕСТ`, затем таблица по 4 тонам,
exit code 0 при PASS или 5 при FAIL.

**Критерий успеха (PASS):**

- все 4 тона `supported = true`;

**Критерий неудачи:** хотя бы один тон не поддержан. Сначала проверить:
громкость, усиление микрофона, выбранные устройства, отсутствие mute. Только

**Разрешённые действия после FAIL (по порядку):**

2. повторить на WASAPI-устройстве (обычно 8/9), если MME не проходит;

4. зафиксировать результат и **не** менять рабочие частоты без решения

## Шаг 10. Относительная АЧХ по одному прогону (без звука)

В одном прогоне шага 7 все тоны передавались с одинаковой цифровой амплитудой
0.5, чему соответствует уровень тона ≈ −9.03 dBFS. Разница
`(−9.03 − level_dbfs)` — это суммарное ослабление тракта для данной частоты,
включая громкость динамика, усиление микрофона и обработку Windows. Это
**относительная** характеристика одного прогона, а не паспортная АЧХ.

Таблица уже печатается `calibrate.py` и хранится в `results\sn014\full-grid.json`
в массиве `tones` (`frequency_hz`, `level_dbfs`, `snr_db`,
`frequency_offset_hz`, `clipped_samples`, `supported`, `reason`).

Для быстрого извлечения таблицы:

```powershell
python -c 'import json; d=json.load(open("results/sn014/full-grid.json", encoding="utf-8")); [print("%7.0f Hz  RX %7.1f dBFS  att %6.1f dB  SNR %5.1f dB  %s" % (t["frequency_hz"], t["level_dbfs"], -9.03 - t["level_dbfs"], t["snr_db"], "OK" if t["supported"] else t["reason"])) for t in d["tones"] if t["level_dbfs"] is not None]'
```

**Критерий успеха:** таблица построена для всех тонов с `level_dbfs != null`;
для каждой частоты указано, поддержана она или нет, и почему.

**Важно:** `response.py` (сравнение TX/RX WAV) требует, чтобы оба файла имели
**общий отсчёт 0**, то есть были записаны с одного старта. Сегодняшний
`calibrate.py` сохраняет только запись микрофона; отдельная пара TX/RX с общим
временем не создаётся. Поэтому сравнение `response.py` на физических данных
**не выполняется** и остаётся `PENDING`. Синтетическая проверка `response.py`
выполнена в тестах. Если позже появится выровненная пара (loopback или
двухканальная запись), команда такая:

```powershell
python response.py --tx <TX.wav> --rx <RX.wav> --plan <TX.json> --channel 0 --json results\sn014\response.json --csv results\sn014\response.csv --plot results\sn014\response.png
```

Нельзя выдавать FAIL `response.py` на невыровненной паре за измерение
ослабления: это артефакт синхронизации.

| `SN-014 CALIBRATION PASS` | шаг 6 PASS **и** шаг 7 PASS по 18/19 кГц **и** шаги 8–9 согласуются |
| `SN-014 CALIBRATION FAIL` | шаг 6 PASS, но 18/19 кГц не поддержаны; зафиксированы числа и причина |
| `SN-014 CALIBRATION BLOCKED` | шаг 6 FAIL: тракт не проходит даже 1–8 кГц; верхние частоты не проверялись |
| `SN-014 CALIBRATION INCONCLUSIVE` | несогласованные шаги 8–9 или артефакты, мешающие измерению |
| `SN-014 CODE PREPARATION — DONE` | только код и тесты; **не** заменяет калибровку |

`PASS` не означает «модем работает» и не заменяет SN-022 (Windows ↔ Windows).

## 5. Если что-то пошло не так

| Симптом | Вероятная причина | Действие |
|---|---|---|
| `exit 3` в шаге 6/7 | устройство не выбрано/занято | проверить индексы, закрыть приложения, `--list-devices` |
| `exit 4` | ошибка открытия потока/записи | сменить host API (MME ↔ WASAPI), проверить WAV-путь |
| Все тоны `snr_below_threshold` | микрофон выключен/усиление 0/не тот вход | проверить mute, усиление, устройство по умолчанию |
| Уровень очень низкий, фон высокий | усиление/шумоподавление Windows | поднять усиление, отключить улучшения, повторить шаг 3 |
| `clipping` | слишком громко/высокое усиление | уменьшить громкость или `--amplitude` |
| Пик есть, но частота смещена | передискретизация/дрейф | записать смещение; не расширять порог без решения |
| Пик у Найквиста | артефакт Windows/драйвера (наблюдение SN-010) | не считать сигналом, описать в отчёте |
| `response.py` FAIL на всех точках | TX и RX не выровнены по времени | не измерение; пометить `PENDING` |

## 7. Ограничения плана

- Одна машина: динамик и микрофон находятся близко, это не модель
  «Компьютер A → Компьютер B» и не проверка дальности.
- Windows может применять AGC, шумоподавление и передискретизацию; инструменты
  это не отключают и не компенсируют.
- Уровни зависят от громкости и усиления; абсолютные dBFS не являются
  свойством динамика или микрофона.
- Тон-сетка не измеряет задержку, реверберацию, многолучёвость, доплер и BER.
- Поддержка 16–22 кГц не гарантирована ни одним устройством до фактического
  измерения; список форматов драйвера этого не доказывает.
- Результат относится только к этому оборудованию, этому помещению и этим
  настройкам в это время.
