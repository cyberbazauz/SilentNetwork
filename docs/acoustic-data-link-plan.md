# План: Acoustic Data Link v0 — передача данных через звук

**Статус:** PROPOSED — ждёт решения Product Owner  
**Дата:** 2026-11-02  
**Автор:** Agent 1  
**Связанные документы:** `docs/decisions/ADR-001-acoustic-frame-v1.md`, `docs/current-milestone.md`, `TASK_BOARD.md`

## 1. Что уже есть и чего ещё нет

| Компонент | Фактическое состояние |
|---|---|
| Кадр Frame v1 | реализован: преамбула 32 бита, sync `0x1ACF`, версия, длина, payload, CRC-16/CCITT-FALSE; служебная часть 88 бит |
| BFSK/CPFSK модулятор | реализован и детерминирован в файлах |
| BFSK-демодулятор | реализован для WAV: поиск преамбулы, некогерентная демодуляция, проверка sync/версии/длины/CRC |
| Windows Desktop Lab | умеет генерировать и проигрывать одиночный тон, импортировать и анализировать запись телефона |
| Android Audio Lab | умеет генерировать тон, записывать WAV, анализировать спектр и показывать вердикт |
| Передача текста через звук | **не реализована ни на Windows, ни на Android** |
| Приём и декодирование кадра на Android | **не реализованы** |
| Запись с микрофона и декодирование на Windows | **не реализованы** |
| SCNP, криптография, ACK/повторы | не реализованы и в этот этап не входят |

Физически подтверждён только тон 1 кГц: запись телефона дала 999.9 Гц при ожидаемых
1000 Гц. Полоса 18–19 кГц в этой записи практически пустая (−103.18 dBFS), поэтому
ультразвуковой тракт пока не подтверждён.

## 2. Цель этапа

Доказать передачу реальных данных через воздух, а не только тона:

1. **Windows → Android:** ноутбук передаёт UTF-8 текст в кадре Frame v1, Android
   записывает звук, декодирует кадр, проверяет CRC и показывает текст.
2. **Android → Windows:** обратное направление с записью на микрофон ноутбука.
3. Сохранить для каждого опыта WAV, JSON и фактические метрики.
4. Повторить опыт на нескольких расстояниях и честно посчитать успешность.

**Первый успех** — один кадр с текстом, принятый без ошибок и с совпавшим CRC,
на расстоянии около 30 см. Это ещё не PASS всего этапа, а первая доказанная
передача данных.

**PASS этапа** — серия опытов по утверждённому протоколу с указанными ниже
порогами и отсутствием ложных срабатываний на шуме.

## 3. Что в этот этап не входит

- SCNP, идентичность, ключи, AEAD и защита от подмены;
- ACK/NACK, повторы, гарантированная доставка;
- передача файлов, потоковое аудио, реальный времени-непрерывный режим;
- mesh, relay, store-and-forward;
- гарантия неслышимости или работа на 18–22 кГц как обязательное условие;
- заявления о дальности 50–100 м.

CRC-16 обнаруживает случайные ошибки, но **не аутентифицирует** отправителя.
На этом этапе нельзя передавать секреты или личные данные.

## 4. Решение по физическому уровню (предложение)

### 4.1 Почему сначала слышимый диапазон

- 1 кГц уже подтверждён реальной записью с телефона.
- 18–19 кГц в той же записи не обнаружены; многие телефоны и ноутбуки режут
  этот диапазон фильтрами и не заявляют его поддержку.
- Для доказательства самого факта передачи данных нужен максимально надёжный
  тракт, а не самый незаметный.
- Ультразвук остаётся отдельным экспериментом после того, как заработает
  базовая передача.

Слышимый сигнал — это тестовый режим, а не обещание продукта.

### 4.2 Профили

| Профиль | Fs | mark / space | Символьная скорость | Назначение |
|---|---:|---|---:|---|
| `data-audible` | 48 000 Гц | 1200 / 2200 Гц | 300 бод | основной профиль первого теста |
| `data-robust` | 48 000 Гц | 1000 / 2000 Гц | 100 бод | запасной вариант, если основной даёт высокий PER |
| `bfsk-18k` | 48 000 Гц | 18 000 / 19 000 Гц | 300 бод | только сравнение, не критерий приёмки |

Все профили должны проходить существующую валидацию `BfskProfile`:
частоты ниже Найквиста, разнос не меньше символьной скорости, `sample_rate`
делится на `symbol_rate` нацело, амплитуда в допустимом диапазоне.

Для `data-audible` и `data-robust` предлагается амплитуда 0.30, рампа 5 мс,
тишина 1000 мс перед кадром и 500 мс после. Это даёт время нажать запись на
телефоне и не обрезает хвост кадра.

### 4.3 Длительность

Кадр занимает `88 + 8·N` бит.

| Payload | Бит | `data-audible` (300 бод) | `data-robust` (100 бод) |
|---:|---:|---:|---:|
| 32 байта | 344 | 1.15 с | 3.44 с |
| 64 байта | 600 | 2.00 с | 6.00 с |
| 512 байт | 4184 | 13.95 с | 41.84 с |

Для первых опытов payload ограничивается **64 байтами UTF-8**. Полный лимит
Frame v1 (512 байт) остаётся в формате, но не используется в приёмке v0.

## 5. Контракт данных (предложение)

### 5.1 Кадр

Frame v1 не меняется. Любое изменение раскладки требует новой версии кадра,
обновления ADR-001 и новых тестовых векторов.

```text
преамбула 32 бита | sync 0x1ACF 16 | версия 1 байт | длина 2 байта BE |
payload N байт | CRC-16/CCITT-FALSE 2 байта
```

Payload — UTF-8 текст. Пустой payload запрещён. Для v0 максимум 64 байта.

### 5.2 Приёмник

Текущий файловый приёмник требует совпадения преамбулы 32/32. Для реального
акустического канала это может быть слишком строго. Предлагается добавить
режим `acoustic`:

- порог преамбулы 28/32 вместо 32/32;
- окончательное решение всё равно принимается по sync word, версии, длине и CRC;
- если CRC не совпал, кадр не считается принятым;
- строгий режим 32/32 остаётся по умолчанию для файловых тестов и benchmark.

Это изменение поведения должно быть параметром, а не скрытой заменой строгой
проверки.

### 5.3 Ошибки

Приёмник различает и показывает человеческим языком:

- сигнал не найден;
- преамбула найдена, но sync word не совпал;
- неподдерживаемая версия;
- длина вне допустимого диапазона;
- запись обрезана, кадр не помещается;
- CRC не совпал (данные повреждены);
- запись пустая или формат WAV неверный.

### 5.4 JSON-отчёт

Предлагаемая схема: `silentnetwork.acoustic-lab.data-link/1`.

Обязательные поля: направление, профиль, payload в hex и SHA-256, длина,
длительность, параметры устройств, время, результат декодирования, тип ошибки,
фактические метрики записи (RMS, peak, clipping), путь к WAV.

Для успешного кадра дополнительно: совпавший CRC, decoded text, `start_time_s`,
`preamble_matches`.

## 6. Изменения Windows Desktop Lab

Новая карточка **«Передать сообщение»**:

- поле текста с ограничением 64 байта UTF-8 и счётчиком;
- выбор профиля `data-audible` / `data-robust`;
- кнопка «Создать и воспроизвести» с обязательным подтверждением;
- статус: создан WAV, идёт воспроизведение, завершено, ошибка;
- сохранение WAV и JSON, SHA-256.

Новая карточка **«Принять сообщение»**:

- выбор входного устройства (микрофон ноутбука);
- длительность записи 10–15 с;
- кнопка «Записать и декодировать»;
- индикатор записи и таймер;
- результат сначала человеческим языком: «Сообщение принято, CRC верный»
  или конкретная причина отказа;
- ниже — decoded text, профиль, длина, время начала кадра, уровень записи;
- сохранение WAV, JSON и отчёта об ошибке.

Ограничения:

- без нажатия кнопки микрофон не открывается;
- без подтверждения звук не воспроизводится;
- системная громкость не меняется;
- при ошибке драйвера показывается фактическая ошибка, а не «успех».

## 7. Изменения Android

### 7.1 Новый DSP-модуль

Добавить в `audiolab/dsp/`:

- `BfskProfile.kt` — параметры профиля и валидация;
- `BfskModulator.kt` — CPFSK, идентичный Python-модулятору;
- `BfskDemodulator.kt` — некогерентная метрика mark/space, поиск преамбулы,
  демодуляция символов;
- `FrameV1.kt` — сборка/разбор кадра и CRC-16/CCITT-FALSE;
- `DataLinkCodec.kt` — текст ↔ UTF-8 ↔ кадр ↔ PCM;
- `DataLinkState.kt` — validation, форматирование и человеческие вердикты.

Демодулятор должен считать метрику эффективно, через накопленные суммы, как
Python-реализация, иначе запись 10–15 с на телефоне будет обрабатываться
слишком долго.

### 7.2 UI

В Audio Lab добавляется раздел **«Передача данных»**:

- поле сообщения (до 64 байт UTF-8);
- профиль;
- «Передать» — подтверждение, генерация PCM, воспроизведение;
- «Принять» — запись 10–15 с, авто-декодирование после остановки;
- результат: принятый текст, CRC, длина, время кадра, причина ошибки;
- экспорт WAV и JSON.

Раздел тоновой калибровки и анализа спектра сохраняется. Тестовый ID и
существующие контракты WAV/JSON не ломаются.

### 7.3 Что не делаем на Android

- не добавляем фейковые `Connected/Online/Delivered`;
- не объявляем приём успешным без CRC;
- не добавляем криптографию до появления SCNP;
- не меняем существующий анализ тона и WAV-контракт.

## 8. Кросс-языковая совместимость

Python и Kotlin должны давать совместимый кадр и совместимую модуляцию.
Предлагается единый набор тестовых векторов:

- ASCII payload;
- UTF-8 payload с кириллицей;
- payload ровно 64 байта;
- негативные случаи: пустой payload, 65 байт, повреждённый CRC, обрезанный кадр.

Проверки:

1. Python строит кадр и PCM, Kotlin декодирует этот PCM.
2. Kotlin строит кадр и PCM, Python декодирует этот PCM.
3. Совпадают frame bits, CRC и текст.
4. PCM SHA-256 может отличаться в последнем разряде между ОС; это
   документируется, а не скрывается. Совместимость проверяется по декодированию,
   а не только по хешу.

Для автоматизации добавляется скрипт, который прогоняет обе стороны и сохраняет
фактические результаты.

## 9. Физический тест

Пошаговый протокол с фиксированными текстами, таблицей результатов и правилами
фиксации артефактов: `docs/sn028-physical-test-protocol.md`.

### 9.1 Подготовка

- телефон и ноутбук на расстоянии 30 см, затем 1 м, затем 3 м;
- тихая комната, телефон не на мягкой поверхности;
- громкость телефона/ноутбука фиксируется и записывается;
- на Android выбирается `UNPROCESSED`, если устройство его поддерживает;
- на ноутбуке проверяется уровень микрофона;
- перед серией выполняется короткая проверка тона 1 кГц.

### 9.2 Процедура Windows → Android

1. На Android открыть «Принять», выбрать 10–15 с и нажать запись.
2. На Windows ввести фиксированный текст, нажать «Передать», подтвердить.
3. Дождаться окончания записи; Android автоматически декодирует.
4. Сохранить WAV и JSON.
5. Повторить 5 раз для быстрой проверки, затем 10 раз для приёмки.

### 9.3 Процедура Android → Windows

1. На Windows выбрать микрофон и нажать «Записать и декодировать».
2. На Android нажать «Передать» и подтвердить.
3. Дождаться конца записи и декодирования.
4. Сохранить WAV и JSON.

### 9.4 Предлагаемые пороги PASS

Пороги нужно утвердить до начала серии, иначе результат нельзя считать приёмкой.

| Условие | Предлагаемый порог |
|---|---|
| 30 см, `data-audible`, 10 опытов | ≥ 9/10 верных CRC и точного текста |
| 1 м, `data-audible`, 10 опытов | ≥ 9/10 |
| 3 м, `data-audible`, 10 опытов | ≥ 7/10 |
| 10 записей только шума | 0 ложных кадров |
| Обратное направление | отдельный порог после первого замера уровня микрофона |

Если основной профиль не достигает порога, серия повторяется на
`data-robust`; результат обоих профилей публикуется.

## 11. Риски и меры

| Риск | Мера |
|---|---|
| Микрофон ноутбука очень тихий (ранее ≈ −90 dBFS RMS) | измерить уровень, включить усиление микрофона ОС, начать с 30 см; если не хватает — зафиксировать ограничение, не подменять результат |
| AGC/шумоподавление телефона искажает BFSK | использовать `UNPROCESSED`, проверить фактический маршрут, повторить на другом устройстве |
| Строгая преамбула 32/32 не срабатывает в воздухе | режим `acoustic` 28/32 + обязательный CRC |
| Слышимый сигнал мешает и ловит бытовой шум | тест в тихой комнате, короткие кадры, профиль `data-robust` при необходимости |
| Нет FEC и повторов | сначала измерить PER; FEC/повторы — отдельная задача после фактических данных |
| Разная частота дискретизации Android | профили кратны и 48 000, и 44 100 Гц; фактическая частота пишется в JSON |
| Ложное «успешно» из-за случайного совпадения | CRC + фиксированный текст + проверка длины + серия на шуме |
| Нет криптографии | явно указано в UI и отчёте; секреты не передавать |

## 12. Решения, которые нужны от Product Owner

1. Утвердить слышимый диапазон `1200/2200 Гц`, 300 бод, как основной для
   первого доказательства, а 18–19 кГц оставить экспериментом.
   Альтернатива: сразу пытаться на 18–19 кГц, но текущая запись этого не
   подтверждает.
2. Утвердить приоритет направления: сначала Windows → Android, затем обратное.
   Альтернатива: сразу оба направления.
3. Утвердить лимит payload 64 байта UTF-8 для v0.
4. Утвердить пороги PASS из §9.4 или заменить их.

После утверждения этих пунктов можно начинать SN-024 без изменения DSP,
Frame v1 и существующих WAV/JSON-контрактов.
