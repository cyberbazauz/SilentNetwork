# SN-028 — протокол физического теста передачи данных через звук

**Статус:** APPROVED — Product Owner, 2026-11-03 (пороги); объём направлений
уточнён Product Owner 2026-11-03  
**Дата:** 2026-11-03  
**Связанные:** `docs/acoustic-data-link-plan.md` §9, `docs/acoustic-data-link.md`, `TASK_BOARD.md`

Утверждённые параметры (менять только с разрешения Product Owner):

| Параметр | Значение |
|---|---|
| Основной профиль | `data-audible` |
| Резервный профиль | `data-robust` (только диагностическая серия) |
| Направления | Windows → Android выполняется сейчас; Android → Windows — `PENDING EXTERNAL MICROPHONE` |
| Максимальный payload | 64 байта UTF-8 |
| 30 см | PASS = 10/10 |
| 1 м | PASS = не менее 8/10 |
| 3 м | исследовательское измерение, обязательного PASS нет |
| `bfsk-18k` | не профиль приёмки SN-028 |

Документ описывает, как именно проводится физический прогон, что фиксируется и
при каких условиях результат считается PASS. До утверждения порогов Product Owner
любой прогон является предварительным измерением, а не приёмкой.

**Уточнение объёма 2026-11-03:** встроенный микрофон ноутбука признан
нерабочим (подтверждено Product Owner). Поэтому на текущем этапе выполняется
только направление Laptop → Phone. Phone → Laptop не тестируется нерабочим
входом, не входит в статистику SN-028 и ждёт внешний микрофон. Профили,
payload и пороги PASS не изменены.

## 0. Быстрый старт (Laptop → Phone, 30 см)

Что нужно: ноутбук с рабочим динамиком, телефон с рабочим микрофоном, кабель
или ручная передача файла.

1. Windows: запустить `dist\SilentNetwork-Desktop.exe` (Python не нужен).
2. Android: установить `dist\SilentNetwork-Android.apk` (debug-сборка) и
   разрешить `RECORD_AUDIO`.
3. Windows: в разделе «Передача данных» выбрать `data-audible`, ввести текст M1,
   нажать «Создать WAV» (только файл, без звука).
4. Android: открыть раздел «Передача данных», выбрать `data-audible`, нажать
   «Записать» и разрешить запись.
5. Windows: нажать «Воспроизвести» и подтвердить PLAY.
6. Android: через 3–4 с остановить запись, дождаться декодирования, проверить,
   что текст и CRC совпали; экспортировать WAV и JSON.
7. Повторить 10 раз, не меняя громкость, профиль и положение.

Направление Phone → Laptop пока не выполняется: вход ноутбука нерабочий.
Обратный прогон начнётся после подключения внешнего микрофона.

## 1. Что доказывает и что не доказывает тест

Доказывает: конкретный ноутбук передаёт текстовый кадр Frame v1 через воздух на
конкретный телефон на указанном расстоянии с указанной громкостью, и принятый
текст совпадает с отправленным при верном CRC-16. Обратное направление будет
доказано отдельно после подключения рабочего внешнего микрофона.

Не доказывает: гарантированную неслышимость, дальность 50–100 м, работу на всех
устройствах, конфиденциальность. CRC-16 не является аутентификацией. Передавать
секреты и личные данные в этом тесте запрещено.

## 2. Оборудование и подготовка

Зафиксировать в отчёте:

| Параметр | Значение |
|---|---|
| Ноутбук: модель, ОС | |
| Телефон: модель, Android, производитель | |
| Выходное устройство Windows (динамик) | |
| Входное устройство Windows (микрофон) | |
| Фактический маршрут Android: частота, `UNPROCESSED`/обработка | |
| Громкость Windows (шаги/%) | |
| Громкость Android (шаги/%) | |
| Помещение, фоновый шум | |
| Дата и время серии | |

Правила:

1. Тихая комната, телефон не на мягкой поверхности (не на кровати/полотенце).
2. Оба устройства на одной высоте, динамик ноутбука направлен на микрофон телефона.
3. Расстояние измеряется рулеткой: 30 см, 1 м, 3 м от динамика до микрофона.
4. Громкость выставляется один раз перед серией и не меняется до её конца.
5. Для Laptop → Phone уровень микрофона проверяется на Android по индикатору
   приложения; если Android пишет клиппинг — уменьшить громкость телефона/ноутбука
   нельзя между попытками серии, поэтому серия откладывается и причина фиксируется.
6. Перед серией — контрольный тон 1 кГц **динамик ноутбука → микрофон Android**:
   убедиться, что запись не клиппингует и сигнал заметно выше фона.
7. Ничего не менять между попытками одной серии (профиль, громкость, положение).

## 3. Направление Windows → Android (основное)

Сообщения (фиксированные, без персональных данных):

| ID | Текст | Байт UTF-8 | Зачем |
|---|---|---:|---|
| M1 | `SN-028 link check` | 17 | базовая ASCII-проверка |
| M2 | `Привет, SilentNetwork` | 33 | кириллица, 2 байта на символ |
| M3 | `0123456789abcdefghijABCDEFGHIJ!?` | 32 | цифры, регистр, пунктуация |
| M4 | `SN-028 payload 0123456789 abcdefghijklmnopqrstuvwxyz ABCDEFGHIJK` | 64 | исследовательская проверка максимума payload; в PASS не входит |

M4 передаётся только на 30 см после обязательных 10 попыток и отдельной строкой
в отчёте. Максимальный payload v0 — 64 байта.

Порядок одной попытки:

1. Android: «Передача данных», профиль `data-audible`, длительность записи 10 с,
   нажать запись (микрофон уже выбран в разделе анализа).
2. Windows: «Передать сообщение», ввести текст M1..M3, нажать PLAY и подтвердить.
3. Дождаться окончания записи. Android декодирует автоматически.
4. Записать результат: вердикт, принятый текст, `crc_ok`, преамбула, частота.
5. Сохранить/экспортировать WAV и JSON под именем
   `sn028-w2a-<дистанция>-<Mx>-<номер>.wav|json`.

План попыток:

- 30 см: M1 ×4, M2 ×3, M3 ×3 (10 попыток);
- 1 м: M1..M3 по кругу (10 попыток);
- 3 м: M1..M3 по кругу (10 исследовательских попыток);
- M4 (64 байта) — одна исследовательская передача на 30 см после серии;
- при провале `data-audible` на дистанции — диагностическая серия
  `data-robust` (100 бод), результат публикуется отдельной таблицей и не
  смешивается со статистикой `data-audible`.

## 4. Направление Android → Windows — `PENDING EXTERNAL MICROPHONE`

Встроенный микрофон ноутбука не работает: он отдаёт насыщенный низкочастотный
шум с клиппингом, а контрольный тон 1 кГц в нём не обнаруживается. Product Owner
подтвердил неисправность. Этот вход не используется, повторно не проверяется и
не входит в статистику SN-028.

Для обратного направления нужен рабочий внешний микрофон: проводной микрофон
гарнитуры, USB-микрофон или другой подтверждённый вход. Bluetooth-гарнитура не
используется как основной измерительный маршрут. После подключения внешнего
микрофона направление возвращается в работу отдельным прогоном по тем же
правилам: контрольный тон, 30 см ×10, 1 м ×10, 3 м ×10, WAV/JSON, отдельная
статистика.

Пока внешнего микрофона нет, статус направления — `PENDING EXTERNAL MICROPHONE`.
Его нельзя выдавать за протестированное или включать в общий PASS/FAIL этапа.

Порядок одной попытки (после появления микрофона):

1. Windows: выбрать внешний микрофон, нажать «Записать и декодировать».
2. Android: «Передать» с тем же текстом, подтвердить PLAY.
3. Дождаться окончания записи и декодирования на Windows.
4. Сохранить WAV/JSON: `sn028-a2w-<дистанция>-<Mx>-<номер>`.

Серия: 30 см ×10, 1 м ×10, 3 м ×10 (исследовательски), тексты M1..M3 по кругу.

## 5. Ложные срабатывания

10 записей по 10 с в той же комнате при выключенном передатчике (шум, речь,
шаги). Ожидание: 0 кадров с верным CRC. Любой кадр — FAIL и разбор причины.

## 6. Критерии PASS (утверждены Product Owner 2026-11-03)

| Условие | Порог |
|---|---|
| 30 см, `data-audible`, 10 попыток | 10/10 точных текстов при `crc_ok` |
| 1 м, `data-audible`, 10 попыток | ≥ 8/10 |
| 3 м, `data-audible`, 10 попыток | измеряется, обязательного PASS нет |
| 10 записей шума | 0 кадров с верным CRC |
| Windows → Android | условие PASS текущего этапа |
| Android → Windows | `PENDING EXTERNAL MICROPHONE`; в PASS текущего этапа не входит |

Порог обратного направления после появления внешнего микрофона — тот же
(30 см 10/10, 1 м ≥ 8/10), но его результаты публикуются отдельно и не
смешиваются с текущей серией Laptop → Phone.

Дополнительно фиксируется: частота дискретизации записи, `preamble_matches`,
`crc_ok`, RMS/Peak dBFS, клиппинг. Если Android отдал 44 100 Гц вместо 48 000,
это записывается; скрытого ресемплирования нет.

PER считается по всем попыткам, включая ошибки синхронизации, неверный CRC,
неполные кадры и неверный текст. В v0 нет автоматических повторов, поэтому
first-attempt PER совпадает с итоговой доставкой; если повторы появятся,
публикуются оба показателя отдельно.

## 7. Что сохраняется для каждой попытки

WAV и JSON пишутся автоматически обоими приложениями. В JSON/сводке должны
быть: `test_id`, `profile`, `payload_length`, `expected_payload` (hex и текст),
`actual_payload`, `crc_ok`, результат преамбулы/синхронизации (`preamble_matches`,
`sync_ok`), обнаруженная частота (`detected_hz`), уровень сигнала (RMS/Peak
dBFS), SNR — только если он корректно вычислим, `duration_s`,
`sample_rate_hz`, `route` (фактическое устройство и host API), `distance`,
`attempt`, `result`, `failure_reason`.

Сводная таблица (заполняется вручную из JSON; JSON — источник истины):

| № | Направление | Дистанция | Текст | Профиль | Декодировано | Текст совпал | CRC | Преамбула | Заметки |
|---:|---|---|---|---|---|---|---|---|---|
| 1 | W→A | 30 см | M1 | data-audible | | | | | |

Итог серии: `<N>/10` на каждую дистанцию, число ложных кадров, фактический
профиль, ограничения. PASS заявляется только при выполнении всех строк §6
одновременно. Неудачные попытки не исключаются из статистики; повтор серии
допустим только при документированной технической ошибке измерительной
установки (например, отсоединён микрофон), и это указывается в отчёте.

## 8. Артефакты и отчёт

- WAV/JSON остаются локально (`acoustic-lab/results/sn028/`, вне git).
- В репозиторий коммитится только отчёт
  `acoustic-lab/results/sn028-physical-test.md` с таблицей, командами, версиями
  приложения (commit), моделями устройств, фактическими маршрутами и честным
  PASS/FAIL.
- Если серия не выполнялась, отчёт с результатами не создаётся, а в
  `TASK_BOARD.md` статусы ведутся раздельно: Laptop → Phone — по фактической
  готовности устройства, Phone → Laptop — `PENDING EXTERNAL MICROPHONE`.
  Preflight-измерения публикуются отдельно:
  `acoustic-lab/results/sn028-preflight.md`.
