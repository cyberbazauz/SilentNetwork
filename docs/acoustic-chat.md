# Непрерывный акустический чат v0

**Статус:** PROPOSED; Python-ядро, Windows Desktop Lab и Android Messenger
реализованы 2026-11-04. 2026-11-05 исправлены потеря кадров на границе
микрофонных блоков и скорость кодирования на Android. 2026-11-07 в Python
Desktop Lab добавлен опциональный режим ART/1 с подтверждением доставки.
Проверка на реальном телефоне и передача через воздух не выполнялись.
**Связанные:** `docs/acoustic-data-link.md`, `docs/acoustic-file-transfer.md`,
`docs/acoustic-reliable-transport.md`, `docs/sn028-next-plan.md`, ADR-001

Документ описывает режим чата, в котором ноутбук и телефон постоянно слушают
микрофон, а отправка сообщения или файла сразу запускает звук. Режим не меняет
Frame v1, CRC-16/CCITT-FALSE, BFSK/CPFSK, профили, лимит payload 64 байта и
файловый контракт v0.

## 1. Цель и границы

Цель: убрать из пользовательского сценария отдельные шаги «создать WAV»,
«подтвердить PLAY» и «записать микрофон». Пока открыт чат, приёмник слушает
непрерывно и разбирает кадры по мере поступления звука.

Что входит в v0:

- непрерывный захват микрофона без фиксированной длительности;
- потоковый поиск и декодирование Frame v1 по скользящему PCM-буферу;
- текст UTF-8 до 64 байт и файл File Transfer v0 до 8192 байт;
- автоматическая сборка файла и проверка SHA-256;
- полудуплекс: приём приостанавливается на время собственного воспроизведения;
- отдельные записи чата для Windows Desktop Lab и Android Messenger.

Что **не** входит в v0:

- подтверждение доставки по умолчанию: успешный PLAY не доказывает приём;
  опциональный ART/1 описан в §2.4 и включается отдельно;
- шифрование, аутентификация отправителя и SCNP/AEAD;
- подавление эха и одновременная передача в обе стороны;
- история сообщений, фоновый сервис Android и доставка после закрытия экрана;
- файлы больше 8192 байт и докачка вне ART/1;
- phone → laptop: направление ждёт внешний микрофон ноутбука.

CRC-16 подтверждает только целостность отдельного кадра. SHA-256 подтверждает
целостность собранного файла. Ни то, ни другое не является аутентификацией:
подмена возможна, секреты и личные данные передавать нельзя.

## 2. Как устроен приём

```
микрофон → PCM-блоки → очередь → StreamingFrameDecoder → ChatSession
                                      │                    │
                                      │                    ├── текст UTF-8
                                      │                    └── файловые пакеты
                                      └── абсолютное смещение кадра
```

### 2.1 Потоковый декодер

Python: `acoustic-lab/snlab/chat.py::StreamingFrameDecoder`  
Android: `audiolab/datalink/StreamFrameDecoder.kt`

- Декодер хранит только хвост PCM, достаточный для самого длинного кадра
  (payload 64 байта) плюс шаг декодирования.
- Разбор начинается после накопления
  `min_decode_samples = max(preamble_span, sample_rate // 4)` и выполняется не
  чаще `decode_step_samples = sample_rate // 2`.
- Кандидаты преамбулы проверяются с порогом 28/32
  (`ACOUSTIC_MIN_PREAMBLE_MATCHES`), CRC-16 остаётся арбитром кадра.
- Кандидаты перебираются в порядке возрастания позиции в буфере. Периодическая
  преамбула `1010…` даёт ложный кандидат на два символа раньше настоящего
  старта; выбор «лучшего» кандидата и окна ±4 символа вокруг него мог не
  содержать настоящий старт, и кадр терялся.
- Если кандидат прошёл преамбулу, sync word, версию и длину, но буфер
  закончился внутри объявленного кадра (`IncompleteFrame`), декодер сохраняет
  этот кадр и ждёт остаток. Ошибка sync word от более раннего ложного
  кандидата больше не побеждает настоящий неполный кадр: именно это теряло
  сообщения и файловые пакеты, разрезанные границей блока микрофона.
- Неполный кадр остаётся в буфере и декодируется, когда придёт остаток. Короткий
  кадр без последующего звука требует `flush()` (Python) или ещё примерно
  0.5 с потока.
- При разрыве потока сбрасывается только PCM-буфер. Пары «кадр-смещение»
  выдаются с абсолютным номером отсчёта, чтобы UI мог показать место приёма.

### 2.2 Сессия чата

Python: `ChatSession`; Android: `ChatSession.kt`.

- Payload, начинающийся с `SF` (`0x53 0x46`), считается файловым пакетом и
  передаётся в `FileAssembler`. Остальные payload декодируются как UTF-8.
- Текст, начинающийся с `SF`, отправитель отклоняет: иначе получатель не сможет
  отличить его от файлового пакета.
- `transfer_id` разделяет передачи. При новом `transfer_id` незавершённая
  сборка освобождается.
- `FileCompleted` выдаётся один раз на `transfer_id`; повтор END или MANIFEST
  не создаёт второе событие.
- Файл сохраняется только после полного набора чанков и совпадения SHA-256.
  Каталог: `rx-<millis>-<transferId>/` внутри каталога приёма.
- Ошибки кадра (`payload_utf8_error`, `file_packet_invalid`,
  `stream_decode_error`) не останавливают прослушивание. Ошибка сборки или
  записи файла приходит как `FileFailed`.

### 2.3 Полудуплекс

Перед собственным PLAY вызывающая сторона вызывает `pause()` захвата, после
окончания — `resume()`. Микрофон при этом не закрывается, но принятые в паузе
блоки отбрасываются. После возобновления декодер получает `on_gap("pause")` и
сбрасывает PCM-буфер: кадр, пересекающий границу паузы, неполный.

Переполнение очереди обрабатывается так же: очередь очищается, приходит
`on_gap("overflow")`. Уже принятые файловые чанки при этом сохраняются — у
отправителя нет повторов, и разрыв не должен уничтожать корректные пакеты.

### 2.4 ART/1 в Python-чате (SN-036)

На Windows Desktop Lab вкладка «Чат» имеет чекбокс «Подтверждать доставку
(ART/1)». Он выключен по умолчанию; обычный текст и File Transfer v0 работают
как раньше. При включении обе стороны должны слушать микрофон и использовать
один профиль: тайминги ART/1 не передаются в пакетах.

- Отправитель кодирует раунд (`MANIFEST`, при необходимости `META`, до 12
  `DATA`) в один массив отсчётов и воспроизводит его, приостановив микрофон.
- После раунда он слушает `STATUS` с битовой картой и повторяет только
  отсутствующие чанки. `STATUS`/`ABORT` принимаются из непрерывного потока
  тем же `ChatSession`, что и обычные кадры.
- Приёмник собирает блок, проверяет длину и SHA-256 и отвечает `STATUS`
  автоматически. `complete=1` и совпавший SHA-256 — единственный признак
  доставки в этом режиме.
- Текст передаётся как UTF-8 и показывается в логе как «Принято (ART/1)».
  Файл сохраняется в `results/chat-received/art-<millis>-<transferId>/`.
- Во время передачи кнопки отправки блокируются; «Стоп» отменяет передачу
  локально. Лимит — 8192 байта на текст или файл.
- ART/1 отличается от File Transfer v0 версией в payload: `SF 02` против
  `SF 01`. Текст, начинающийся с `SF`, по-прежнему отклоняется.
- SHA-256 и CRC-16 не аутентифицируют отправителя. Режим пригоден только для
  несекретных лабораторных данных до внедрения SCNP/AEAD.

Реализация: `snlab/reliable.py`, `snlab/reliable_chat.py`, `snlab/chat.py`
(`enable_transport`/`poll_transport`) и `desktop_app.py`.


## 3. Передача

Отправка из чата не создаёт WAV. Текст кодируется в Frame v1 и сразу
превращается в отсчёты (`encode_text_message` / `DataLinkCodec.encodeToPcm`).
Файл кодируется в последовательность пакетов и отсчёты одним массивом
(`encode_file_message` / `FileTransferCodec.encodeFileToPcm`).

В режиме ART/1 звук строится раундами: тишина 0.10 с перед раундом, 0.05 с
после, пауза 0.25 с между кадрами; ответ `STATUS` — 0.05 с тишины с обеих
сторон. Таймауты (`ack_guard` 500 мс, `ack_margin` 1500 мс, `turnaround`
300 мс) пересчитываются от символьной скорости профиля. Параметры должны
совпадать у отправителя и приёмника.

Параметры по умолчанию:

| Параметр | Значение |
|---|---|
| Основной профиль Windows-чата | `data-audible` (1200/2200 Гц, 300 бод) |
| Диагностический профиль Windows-чата | `data-robust` (1000/2000 Гц, 100 бод) |
| Android-режимы чата | `chat-normal` (1200/2200 Гц, 300 бод), `chat-excellent` (1000/2000 Гц, 150 бод), `chat-highfreq` (16000/17500 Гц, 100 бод) |
| Максимум текста | 64 байта UTF-8 |
| Максимум файла | 8192 байт |
| Тишина перед сообщением в чате | 0.2 с |
| Тишина после сообщения в чате | 0.1 с |
| Длительность кадра 64 байта | ≈1.96 с на `data-audible` |
| Длительность файла 8192 байта | ≈364 с на `data-audible` |

Файл 8192 байта требует около 420 с записи на приёмнике и большого запаса
памяти: Python выделяет под отсчёты примерно 140 МБ в `float64`, Android
работает с PCM16 и включает `largeHeap`. Эти значения не измерены на реальном
телефоне.

На Android кодирование ускорено: вместо `sin()` на каждый отсчёт осциллятор
продвигается умножением на кэшированную единичную фазору с перенормировкой
раз в символ. Разовый замер на desktop JVM (временный бенчмарк, после замера
удалён): текст 64 байта 4.2 → 1.2 мс; файл 100 байт 30 → 4–6 мс; 1000 байт
57–68 → 16–17 мс; 4096 байт 145–227 → 62–66 мс; 8192 байта 290–325 →
109–111 мс, то есть примерно в 2.7–3.4 раза быстрее. Это время подготовки PCM
до PLAY, а не передачи через воздух.

## 4. Интерфейсы

### 4.1 Android Messenger

Файл: `apps/android/app/src/main/java/org/silentnetwork/app/ui/messenger/`  
Разметка и строки: `res/layout/fragment_messenger.xml`, `res/values/strings.xml`

- При открытии вкладки просит `RECORD_AUDIO` и сразу начинает прослушивание.
- Режим чата (`normal` / `excellent` / `highfreq`) выбирает профиль
  `chat-normal` / `chat-excellent` / `chat-highfreq`. Это те же кадры Frame v1,
  что и у `data-audible`/`data-robust`; общий валидатор
  `BfskProfile.supportedProfiles()` принимает оба семейства профилей.
- Отправка текста — кнопкой или действием клавиатуры; отправка файла — через
  системный выбор файла. Пустой файл отклоняется; имя и размер проверяются.
- На время кодирования и воспроизведения composer блокируется, приём
  приостанавливается. После окончания звука приём возобновляется.
- Кнопка «Стоп» прерывает воспроизведение; приём возобновляется.
- Принятые файлы сохраняются в
  `getExternalFilesDir(null)/received/rx-<millis>-<transferId>/`.
- UI различает исходящее сообщение, входящий текст, системную заметку и ошибку,
  но не показывает фиктивную доставку.

### 4.2 Windows Desktop Lab

Файл: `acoustic-lab/desktop_app.py`, вкладка «Чат».

- При первом выборе вкладки автоматически выбирает встроенный микрофон и
  запускает прослушивание. После ручного «Стоп» авто-старт возобновляется при
  повторном входе на вкладку.
- Можно сменить профиль и микрофон, обновить список устройств.
- Текст отправляется кнопкой или Enter, файл — через диалог выбора. Звук
  начинается сразу, без отдельного подтверждения PLAY.
- Чекбокс «Подтверждать доставку (ART/1)» включает раунды с ожиданием
  `STATUS`. Переключать его на лету можно только при остановленном приёме:
  сессия перезапускается, потому что меняется конфигурация приёмника.
- На время звука приём приостанавливается. Кнопка «Стоп звука» прерывает PLAY,
  а во время ART/1 также отменяет передачу.
- Принятый `STATUS` автоматически кодируется и воспроизводится; повтор
  потерянного статуса приходит со следующим раундом отправителя.
- События приходят из потока захвата через очередь и обрабатываются в Tk через
  `root.after`, а не напрямую из аудиопотока.
- Принятые файлы сохраняются в `results/chat-received/rx-<millis>-<transferId>/`.
- При закрытии окна захват и воспроизведение останавливаются.

## 5. Ошибки и поведение

| Ситуация | Поведение |
|---|---|
| Повреждённый кадр / CRC не сошёлся | Кадр отброшен, приём продолжается |
| Payload не UTF-8 | `FrameFailed(payload_utf8_error)`, приём продолжается |
| `SF`-payload не является файловым пакетом | `FrameFailed(file_packet_invalid)` |
| Разрыв или переполнение микрофонного потока | Сброс PCM-буфера, `on_gap`, приём пересинхронизируется |
| Конфликт файловых пакетов | `FileFailed`, частичная сборка освобождается |
| Неполный файл | Файл не создаётся; `FileCompleted` не выдаётся |
| Ошибка записи файла | `FileFailed(output_error)`, SHA-256 всё равно рассчитан |
| Текст длиннее 64 байт | Отправка отклоняется до PLAY |
| Текст начинается с `SF` | Отправка отклоняется до PLAY |
| Файл больше 8192 байт | Отправка отклоняется до PLAY |
| PLAY завершился ошибкой | Статус ошибки; приём возобновляется |
| ART/1 включён без прослушивания | Отправка отклоняется: без STATUS доставка не подтверждается |
| `STATUS` не принят за окно | Повтор набора; после 5 раундов без прогресса — ошибка `ack_timeout` |
| SHA-256 не совпал | `ABORT(hash_mismatch)`, блок не выдаётся и не сохраняется |
| `STATUS` потерян | Приёмник ответит заново на следующий раунд; отправитель повторит набор |
| ART/1-пакет при выключенном режиме | `FrameFailed(transport_disabled)`, приём продолжается |
| Отмена ART/1 пользователем | Локальная отмена без `ABORT`; приёмник мог не получить все чанки |

Новые регрессионные тесты чата:

- поток блоками по 512 отсчётов с двумя лишними битами периодической
  преамбулы перед кадром;
- кадр, разрезанный блоками по 1024 отсчёта, при σ = 0.01;
- файл 1000 байт, поданный блоками по 512 отсчётов, с проверкой байтов и
  SHA-256;
- файлы 0, 1, 40 и 200 байт, поданные блоками по 4096 отсчётов;
- ART/1: раунд кодируется и разбирается обратно, повторяются только
  отсутствующие чанки, потеря `STATUS` даёт `ack_timeout`, полный обмен
  «раунд → STATUS → done» проходит через синтетический PCM и `ChatSession`;
- GUI ART/1: подтверждение доставки приходит только после `STATUS`,
  приёмник автоматически отвечает, отмена не выдаёт ложный успех.

Эти проверки используют синтетический PCM и фейковые аудиоустройства. Они
доказывают разбор потока, сборку файла и логику раундов, но **не** передачу
через воздух. Разовые замеры кодирования и потокового декодирования
выполнялись временным JVM-бенчмарком, который после замера удалён; в набор
тестов они не входят.

## 7. Что не проверено

- Установка APK и работа чата на реальном телефоне: `adb devices` пуст.
- Реальная передача Laptop → Phone в режиме чата.
- Phone → Laptop: `PENDING EXTERNAL MICROPHONE`; встроенный микрофон ноутбука
  не работает.
- Приём файла 8192 байта и пик памяти на Android и Python.
- Передача ART/1 через воздух, реальные потери `STATUS`, число раундов и
  фактическое время; AIR-тест из `docs/acoustic-reliable-transport.md`
  не выполнялся.
- Android-порт ART/1 и кросс-проверка Python ↔ Kotlin для ART/1.
- Поведение при реальном эхе, AGC и шумоподавлении микрофона (включая ART/1).
- Длительная работа чата без утечек памяти.
- Одновременная работа чата и других вкладок Desktop Lab (кнопки PLAY
  блокируются, но фоновые записи не тестировались).
