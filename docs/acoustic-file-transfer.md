# Acoustic File Transfer v0 — контракт

**Статус:** PROPOSED; Python v0, Windows Desktop Lab и Android-приём реализованы 2026-11-04, ожидает одобрения Product Owner
**Связанные:** `docs/acoustic-data-link.md`, `docs/sn028-next-plan.md`,
`docs/sn028-stage-1-runbook.md`, ADR-001

Документ описывает файловый слой **над** существующим Acoustic Data Link v0.
Frame v1, CRC-16/CCITT-FALSE, BFSK, профили `data-audible`/`data-robust` и
лимит 64 байта payload не меняются.

## 1. Цель и границы

Цель v0: передать небольшой файл как последовательность кадров Frame v1,
собрать его на приёмнике и проверить SHA-256 всего файла.

Что входит в v0:

- произвольные байты: текст, JSON, PNG, небольшой бинарный файл;
- размер файла от 0 до **4096 байт**;
- имя файла до **40 байт UTF-8**;
- один файл за одну передачу, без ACK и повторной отправки;
- пакеты `MANIFEST`, `DATA`, `END`;
- повтор манифеста и завершающего пакета для устойчивости к потерям;
- проверка целостности по SHA-256.

Что **не** входит в v0:

- файлы больше 4096 байт, потоковая передача и докачка;
- ACK/NACK, retransmission, окно и контроль перегрузки;
- шифрование, аутентификация и SCNP/AEAD;
- несколько файлов в одной сессии;
- скрытность, гарантированная дальность и работа на любых устройствах.

CRC-16 в Frame v1 обнаруживает случайные ошибки отдельного кадра. SHA-256 в
`END` проверяет целостность всего файла, но **не аутентифицирует** отправителя:
подмена возможна. Передавать секреты и личные данные в v0 запрещено.

## 2. Раскладка пакета

Пакет целиком помещается в payload Frame v1 (≤64 байта). Все многобайтовые
числа — big-endian.

| Смещение | Размер | Поле | Значение |
|---:|---:|---|---|
| 0 | 2 | `magic` | `0x53 0x46` (`SF`) |
| 2 | 1 | `ft_version` | `1` |
| 3 | 1 | `packet_type` | `1` MANIFEST, `2` DATA, `3` END |
| 4 | 1 | `transfer_id` | `0..255` |
| 5 | 2 | `seq` | DATA: номер чанка; MANIFEST/END: `0` |
| 7 | 2 | `total_chunks` | число DATA-чанков |
| 9 | 1 | `payload_len` | длина payload пакета, `0..54` |
| 10 | `payload_len` | `payload` | зависит от типа |

Заголовок — 10 байт, максимум данных — **54 байта**. Пустой файл не содержит
DATA-пакетов: только MANIFEST и END.

### 2.1 MANIFEST

Payload:

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 1 | `filename_len` |
| 1 | `filename_len` | `filename` в UTF-8 |
| 1+n | 4 | `file_size` |
| 5+n | 1 | `chunk_data_bytes` (в v0 всегда 54) |

Ограничения: `1 ≤ filename_len ≤ 40`, `chunk_data_bytes = 54`,
`file_size ≤ 4096`. Имя проверяется: запрещены `/`, `\`, `..`, управляющие
символы, завершающие точка/пробел и зарезервированные имена Windows.

### 2.2 DATA

Payload — ровно `chunk_data_bytes` байт для всех чанков, кроме последнего.
Длина последнего чанка равна `file_size - seq * 54`. `seq` начинается с 0.

### 2.3 END

Payload:

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `file_size` |
| 4 | 2 | `total_chunks` |
| 6 | 32 | `sha256` всего файла |

`END` повторяется `end_repeats` раз (по умолчанию 2). Приёмник принимает
одинаковые повторы идемпотентно.

## 3. Порядок передачи

```text
MANIFEST
DATA 0
DATA 1
...
DATA N-1
END, END
```

Манифест повторяется после каждых 16 DATA-чанков (по умолчанию). Повтор
содержит те же байты; приёмник не считает его новым файлом.

Приёмник допускает:

- DATA-пакеты в любом порядке;
- повторный MANIFEST или END с теми же байтами;
- DATA до MANIFEST (буферизуется до появления манифеста);
- потерю отдельных кадров, если файл можно собрать не полностью — тогда
  возвращается `incomplete_transfer`, файл не создаётся.

Приёмник отвергает:

- другой `transfer_id`, magic или версию;
- `total_chunks > 76` или `file_size > 4096`;
- чанк с неверной длиной, выходящим номером или другими байтами при повторе;
- несовпадающий повтор MANIFEST/END;
- несовпадение SHA-256;
- небезопасное имя файла.

## 4. Тайминг

Frame v1 с payload 64 байта содержит `88 + 64·8 = 600` бит. Для
`data-audible` при 300 бод это **2.0 с** на кадр. Межкадровая пауза по
умолчанию — **0.25 с**.

| Файл | DATA-чанков | Кадров с повторами | Фактически `data-audible` |
|---:|---:|---:|---:|
| 0 байт | 0 | 3 | 6.6 с |
| 100 байт | 2 | 5 | 10.4 с |
| 1 КиБ | 19 | 23 | ≈ 53 с |
| 4 КиБ | 76 | 83 | 181.9 с |

Фактические значения получены при генерации WAV в Python, а не через воздух.
Оценка включает lead и tail; для `data-robust` при 100 бод время в 3 раза
больше.

## 5. Отчёты

Схема: `silentnetwork.acoustic-lab.file-transfer/1`.

Отчёт передачи содержит: профиль, имя и размер файла, SHA-256, `transfer_id`,
число чанков и пакетов, тайминг, путь и SHA-256 WAV. Отчёт приёма содержит:
число декодированных кадров, ошибки кадров, недостающие чанки, дубликаты,
ожидаемый и фактический SHA-256, путь созданного файла.

Файл создаётся только при полном наборе чанков, совпадающем размере и
совпавшем SHA-256. Иначе результат `error`, файл не пишется.

## 6. CLI

```powershell
cd acoustic-lab

python file_transfer.py send --file note.txt --out results\note.wav --profile data-audible
python file_transfer.py receive --wav results\note.wav --out-dir results\received
```

По умолчанию отчёт передачи пишется рядом с WAV как `<имя>.tx.json`, отчёт
приёма — как `<имя>.rx.json`. Явные пути задаются `--report`. Коды возврата:
`0` — успех, `2` — неверные аргументы или файл, `3` — ошибка WAV/файла,
`4` — передача не восстановлена. `send` создаёт только WAV и JSON и не
воспроизводит звук.

### 6.1 Windows Desktop Lab

`acoustic-lab/snlab/file_transfer_desktop.py` связывает файловый слой с
устройствами Windows и отчётами Desktop Lab:

- `generate_file_message` — файл → WAV + JSON `file-tx-<профиль>-<метка>.json`;
- `play_file_message` — PLAY только после подтверждения, SHA-256 WAV
  перепроверяется перед открытием потока; пишется
  `<имя>.playback-<метка>.json`;
- `receive_file` — запись микрофона 1…300 с, WAV + JSON
  `file-rx-<профиль>-<метка>.json`, собранный файл сохраняется в отдельный
  подкаталог `received/<имя-записи>/`, чтобы не перезаписывать прежние
  приёмы.

В `desktop_app.py` добавлены карточки «Передать файл» и «Принять файл»:
выбор файла, создание WAV, подтверждаемый PLAY, выбор микрофона, запись,
показ имени, размера, SHA-256 и пути сохранённого файла. Схемы отчётов
Desktop Lab: `silentnetwork.acoustic-lab.file-transfer-tx/1`,
`.../file-transfer-playback/1`, `.../file-transfer-receive/1`. Исходная
схема контракта сохраняется в поле `contract_schema`.

`performed=true` в playback-отчёте означает только полное воспроизведение
WAV. Ни создание WAV, ни PLAY, ни успешный round-trip через файл не
доказывают передачу через воздух.

### 6.2 Android Audio Lab

В `AudioLabFragment` добавлена карточка «Файлы через звук» для направления
Laptop → Phone. Kotlin-порт контракта находится в
`audiolab/datalink/FileTransferCodec.kt`: packet codec, `FileAssembler`,
`buildTransferPlan`, `encodeFileToWav`, multi-frame
`decodePacketsFromSamples` с ресинхронизацией и `decodeWavToFile`.

Возможности карточки:

- профиль `data-audible` (по умолчанию) или `data-robust`;
- запись 15, 30 или 60 с; по умолчанию 30 с;
- принятый файл сохраняется в `cacheDir/received_files`;
- показ вердикта, имени, размера, SHA-256, числа кадров/пакетов/чанков и
  параметров записи (RMS, пик, клиппинг);
- экспорт принятого файла и JSON-отчёта через системный picker.

Ограничения те же, что у Windows: один файл 0…4096 байт, имя до 40 байт
UTF-8, без ACK и шифрования. SHA-256 проверяет целостность, но не
аутентифицирует отправителя. Ручная остановка записи считается отменой:
частичный буфер не декодируется и файл не создаётся.

Запись 15/30/60 с вмещает примерно 200 байт, 500 байт и 1 КиБ
соответственно; это оценка по длительности кадров и повторов, а не
гарантированный лимит. Файл 4 КиБ требует около 182 с звука и в одну запись
карточки не помещается. Запись через воздух на Android ещё не выполнялась;
JVM-тесты подтверждают только файловый round-trip через WAV.

### 6.3 Отчёты Android

Отчёт приёма использует схему `silentnetwork.acoustic-lab.file-transfer/1`,
как и Python. Поля: `direction: rx`, профиль, `min_preamble_matches`,
лимиты, WAV (имя и SHA-256), метрики записи, `result`/`error_type`/`message`,
`stream` (кадры, ошибки кадров и пакетов) и `transfer` (id, имя, размер,
чанки, дубликаты, ожидаемый и фактический SHA-256, путь файла). Флаги
`crc_is_authentication` и `sha256_is_authentication` всегда `false`.

### 6.4 Кросс-проверка Python ↔ Kotlin

`acoustic-lab/cross_check_android.py` проверяет оба слоя в обе стороны:
Python WAV → Kotlin-декодер и Kotlin WAV → Python-декодер. Для файлового
слоя дополнительно сверяются имя, размер, число чанков и SHA-256
собранного файла.

Файловые кейсы: текст 40 байт, кириллическое имя 23 байта в `data-robust`,
бинарные 120 байт (3 чанка) и пустой файл 0 байт. Результат фиксируется в
`acoustic-lab/results/sn027-cross-check.md`. Это проверка L0 на JVM и
синтезированном WAV; она не заменяет воздушный тест.

Первый воздушный файл подготовлен отдельно: `docs/sn034-first-air-runbook.md`
(JSON 43 байта, `data-audible`, 30 см, запись 15 с). Артефакты WAV/JSON лежат
локально в `acoustic-lab/results/sn034-first-air/` и не коммитятся.

## 7. Ошибки

| `error_type` | Причина |
|---|---|
| `file_too_large` | файл больше 4096 байт |
| `filename_invalid` | небезопасное или слишком длинное имя |
| `packet_invalid` | magic, версия, тип, длина или поля вне диапазона |
| `manifest_invalid` | повреждённый или противоречивый MANIFEST |
| `transfer_conflict` | разные данные у одного `seq` или разные повторы |
| `incomplete_transfer` | не все чанки или нет MANIFEST/END |
| `hash_mismatch` | SHA-256 собранного файла не совпал |
| `not_file_transfer` | WAV содержит кадр, но не файловый пакет |
| `signal_not_found` | ни одного кадра |
| `wav_not_found`, `wav_format_error` | проблемы входного WAV |

## 8. Тестовые векторы

`acoustic-lab/tests/fixtures/file-transfer-vectors.json` фиксирует точные
байты MANIFEST, DATA и END для файла `note.txt` (12 байт, `Hello, world`,
`transfer_id=7`). Любое изменение раскладки требует новой версии, обновления
векторов и этого документа.

## 9. Дорожная карта

| Этап | Содержание | Статус |
|---|---|---|
| 0 | Контракт, Python-прототип, файловый round-trip через WAV, тесты | реализован: `snlab/file_transfer.py`, CLI, 71 тест; ожидает одобрения PO |
| 1 | Windows Desktop Lab: выбор файла, отправка, приём и сохранение | реализован: `snlab/file_transfer_desktop.py`, карточки в `desktop_app.py`, 19 тестов; воздух не проверялся |
| 2 | Реальный тест 30 см: текст, JSON, PNG; измерения | план |
| 3 | Android: длинная запись, приём и экспорт | реализован код и JVM-тесты: `FileTransferCodec.kt`, карточка «Файлы через звук», 17 тестов; кросс-проверка Python ↔ Kotlin 8/8; воздух не проверялся |
| 4 | ACK/повтор, докачка, файлы больше 4 КиБ | после SN-033 |
| 5 | SCNP/AEAD до любых личных данных | после SN-030…SN-032 |

Этап 0 доказывает только файловый round-trip через синтезированный WAV. Он
**не** доказывает передачу через воздух. Этап 1 добавляет Windows UI и
отчёты PLAY/приёма, но также не заменяет воздушный тест: для этого нужен
этап 2 с записью микрофона и метаданными. Этап 3 добавляет Android-приём, но
его приём через воздух также не выполнен.

Android-карточка файлов пишет не более 60 с. Файл 100 байт (≈10.4 с звука)
помещается в одну запись, 1 КиБ требует около 53 с и близок к лимиту,
4 КиБ требуют около 182 с и в одну запись не помещаются.
