**Проект:** SilentNetwork  
**Компонент:** Android Audio Lab Receiver / Hardware Calibration  
**Версия приложения:** v0.1.0-alpha (SN-015-ANDROID)  
**Ответственный агент:** Agent 2 (Gemini — Android & Application Developer), интеграция Agent 1  
**Статус испытаний:** `CODE ONLY / PHYSICAL TESTING PENDING`  
**Режим на сегодня:** СТРОГО БЕЗ ЗВУКА И БЕЗ ФИЗИЧЕСКОЙ ЗАПИСИ.  
**Дата обновления:** 2026-11-02  
**Причина обновления:** SN-015: приём `LAPTOP → PHONE`, Test ID, expected/detected frequency, фактический маршрут микрофона, WAV/JSON-контракт `docs/hardware-calibration/SN-015-RESULT-FORMAT.md`.

> `AudioRecord.startRecording()` и воспроизведение `AudioTrack.play()` на

## 1. Введение и назначение

Данный план описывает пошаговую методику физического тестирования акустического тракта смартфона с использованием раздела **Audio Lab** приложения SilentNetwork.

Цель испытаний — экспериментально подтвердить:
1. Аппаратную возможность излучателя (динамика) смартфона воспроизводить частоты диапазона 15–22 кГц (включая предварительный профиль BFSK M0: 18–19 кГц).
2. Аппаратную возможность микрофона смартфона захватывать сигналы в диапазоне 15–22 кГц с частотой дискретизации 48 кГц без искажений и программного подавления.
3. Наличие или отсутствие агрессивной фильтрации (AEC, AGC, Noise Suppression, low-pass фильтры) в режиме `AudioSource.UNPROCESSED`.
4. Уровень нелинейных гармоник, паразитных шумов и клиппинга.

> [!IMPORTANT]
> **Контракт CLI Agent 1 (calibrate.py):** физическое воспроизведение и запись
> через ПК разрешены **только** с флагом `--hardware-test`. Без него `calibrate.py`
> отказывает с exit code 2. Это правило безопасности, а не баг.

## 2. Справочник инструментов ПК (Acoustic Lab Agent 1)

Перед использованием команд проверьте их актуальность: `python <tool>.py --help`.

| Инструмент | Роль | Открывает аудиоустройства |
|---|---|---|
| `acoustic-lab/tonegen.py` | Создать тестовый WAV и JSON-план | **нет, никогда** |
| `acoustic-lab/analyze.py` | Посчитать метрики готового WAV | **нет, никогда** |
| `acoustic-lab/transmitter.py` | Кодировать данные → BFSK WAV (файл) | **нет, никогда** |
| `acoustic-lab/calibrate.py --analyze` | Офлайн-анализ записи по тон-плану | **нет** |
| `acoustic-lab/calibrate.py --hardware-test` | Тон-сетка через динамик + запись микрофоном | **да** (play + record) |
| `acoustic-lab/calibrate.py --list-devices` | Показать аудиоустройства | **нет** (опрос PortAudio) |
| `acoustic-lab/scanner.py --capture` | Запись микрофоном без воспроизведения | **да** (record only) |
| `acoustic-lab/scanner.py --list` | Показать устройства и форматы | **нет** |

> [!CAUTION]
> **`transmitter.py --file PATH`** читает **бинарный файл данных** (payload ≤ 512 байт)
> и создаёт BFSK WAV. Это **не аудиоплеер**. Он не воспроизводит WAV через динамик
> и не принимает WAV-файлы на вход.

## 3. Подготовка смартфона к тестированию

Перед началом физического тестирования:

1. **Окружение:**
   - Выберите тихое помещение без посторонних громких звуков, эха и работающих вентиляторов/кондиционеров.
   - Расположите смартфон на мягкой поверхности (ткань, коврик для мыши) во избежание дребезжания корпуса от стола.
2. **Аудионастройки устройства:**
   - Установите громкость мультимедиа телефона на **30–40%** (ни в коем случае не на 100%, чтобы не перегрузить мембрану динамика).
   - Убедитесь, что в настройках звука телефона отключены эквалайзеры, Dolby Atmos, «улучшайзеры» звука и пространственное аудио.
3. **Разрешения:**
   - Предоставьте системное разрешение `android.permission.RECORD_AUDIO` при первом запросе приложения.

## 4. Инструкция по использованию Audio Lab в приложении

### 4.1. Как открыть Audio Lab
- Запустите приложение SilentNetwork.
- Нажмите на вкладку **Audio Lab** в нижней навигационной панели (между «Статус» и «Чат»)  
  *или*  
  Нажмите кнопку **«Открыть Audio Lab (Калибровка)»** на экране «Статус».

### 4.2. Как выбрать частоту и параметры
- В разделе **A. ПЕРЕДАТЧИК (Transmitter)**:
  - **Частота:** выберите из выпадающего списка:
    - `1000 Гц` — для первичной проверки динамика (слышимый контрольный тон);
    - `18000 Гц`, `18500 Гц`, `19000 Гц` — для проверки тестового профиля M0;
    - `15000 Гц`, `16000 Гц`, `17000 Гц`, `20000 Гц`, `21000 Гц`, `22000 Гц` — для сетки частот.
  - **Sample Rate:** оставьте `48000 Гц`.
  - **Длительность:** `2 сек` (или `3 сек`).
  - **Амплитуда:** начните с безопасного значения `0.15 (-16.5 dBFS)`.
  - В поле предпросмотра отобразятся выбранные параметры и цветовой индикатор профиля (`ГИПОТЕЗА M0`).

### 4.3. Как создать тестовый WAV (без звука)
- Нажмите кнопку **«Сгенерировать WAV»**.
- Файл PCM16 mono генерируется в фоновом кэше без воспроизведения звука.
- В строке статуса появится сообщение: `WAV успешно сгенерирован: ... (.wav)`.
- Кнопка **«Анализ тест-сигнала»** станет активной — можно проверить эталонный синтезированный спектр ещё до воспроизведения.

### 4.4. Как воспроизвести тестовый сигнал (физический тест динамика)
> [!WARNING]
> Воспроизведение звука разрешено только в дневное время!
- Нажмите кнопку **«PLAY (Воспроизвести)»**.
- Появится диалоговое окно безопасности:  
  *«Сейчас через динамик телефона будет воспроизведён тестовый сигнал ... на низкой амплитуде. Продолжить?»*
- Нажмите **«Воспроизвести»**.
- Для экстренной остановки нажмите кнопку **«STOP»**.

### 4.5. Как записать сигнал микрофоном (LAPTOP → PHONE)

1. На Windows открыть **Audio Lab Desktop** (`run_desktop.bat`) и выбрать
   тестовый тон. Test ID показан в окне Desktop Lab.
2. В разделе **B. LAPTOP → PHONE RECEIVER** на телефоне:
   - вставьте **TEST ID** с Windows (или оставьте сгенерированный телефоном);
   - выберите **ожидаемую частоту**, совпадающую с частотой Windows;
   - выберите длительность записи: `5 сек`, `10 сек` (по умолчанию) или
     `15 сек`;
   - sample rate: `48 000 Гц` (fallback `44 100 Гц`).
3. Нажмите **«НАЧАТЬ ЗАПИСЬ»**. Запись начинается **только** по этому нажатию;
   фоновый или скрытый захват исключён.
4. Приложение запрашивает `TYPE_BUILTIN_MIC`. Android может проигнорировать
   предпочтение: фактический маршрут и фактический Fs отображаются в строке
   `Маршрут: ...`. Это не ошибка, если маршрут отличается, но он должен быть
   зафиксирован в JSON.
5. В состоянии `RECORDING` нажмите **PLAY** в Windows Desktop Lab.
6. После окончания записи телефон показывает
   `RECORDING COMPLETE`, но **не** заявляет успешный приём: WAV ещё не
   проанализирован.
7. Для досрочной остановки нажмите **«ОСТАНОВИТЬ ЗАПИСЬ»**. `AudioRecord`
   освобождается при остановке, `onPause` и `onDestroyView`.

### 4.6. Как проанализировать запись

- Нажмите **«Передать в анализатор»** в разделе приёмника  
  *или* нажмите **«Импортировать WAV из памяти»** в разделе анализатора.
- Анализатор вычислит на борту устройства:
  - **RMS (dBFS)** и **Peak (dBFS)**;
  - **Клиппинг:** количество перегруженных отсчётов и статус-бейдж;
  - **DC offset**;
  - **Доминирующую частоту** (глобальный пик);
  - **Expected / Detected / Frequency error** — пик в окне ±300 Гц вокруг
    ожидаемой частоты с порогом 6 дБ над медианой окна;
  - **Долю энергии 18–19 кГц**;
  - **Таблицу главных спектральных пиков**;
  - **PSD-график** 0–24 кГц.
- Состояние `ANALYZED` означает только, что анализ выполнен. Оно не означает
  PASS: решение принимает Product Owner по документу
  [`SN-015-LAPTOP-TO-PHONE.md`](../../../docs/hardware-calibration/SN-015-LAPTOP-TO-PHONE.md)
  и контракту [`SN-015-RESULT-FORMAT.md`](../../../docs/hardware-calibration/SN-015-RESULT-FORMAT.md).

### 4.7. Как экспортировать WAV и JSON

- Для WAV: нажмите **«Экспорт записи WAV»** (или «Экспорт тест-WAV»).
  - Имя по умолчанию: `sn015_<test_id>_rx.wav`.
  - Сохраните файл в «Загрузки» или на карту памяти.
- Для JSON: нажмите **«Экспорт JSON-отчёта»**.
  - Имя по умолчанию: `sn015_<test_id>_result.json`.
  - JSON содержит обязательные top-level поля контракта, `wav_sha256`,
    `expected_frequency_hz`, `detected_frequency_hz`, `frequency_error_hz`,
    фактический sample rate и маршрут.
- Оба файла передаются на Windows через кабель или файловый менеджер. Это не
  сетевой транспорт SilentNetwork.

## 5. Обязательная последовательность физических испытаний

> [!IMPORTANT]
> Испытания выполняются **строго последовательно** снизу вверх по частоте. Если
> текущий этап не пройден, следующие **не начинаются**, а результат фиксируется.

### Этап 1. Контрольный тон 1 кГц (проверка работоспособности тракта)

**Цель:** убедиться, что динамик воспроизводит и микрофон записывает слышимый сигнал. Если 1 кГц не проходит — тракт неработоспособен.

**На телефоне:**
1. Частота: `1000 Гц`, длительность: `2 сек`, амплитуда: `0.15`.
2. Нажать «Сгенерировать WAV», затем «PLAY».
3. Убедиться, что тон слышен и чист (без щелчков/искажений).
4. Нажать «НАЧАТЬ ЗАПИСЬ» (3 сек), затем «Передать в анализатор».

**Критерий успеха:**
- Доминирующая частота в анализаторе: 1000 ± 25 Гц.
- Клиппинг: нет.
- Уровень записи выше шумового пола минимум на 15 дБ.

**Критерий неудачи:** тон не слышен, не виден в спектре или доминирует шум → остановить тестирование, проверить громкость и разрешения.

### Этап 2. Диапазон 1–8 кГц (контрольная сетка слышимых частот)

**Цель:** подтвердить, что тракт телефона работает во всём слышимом диапазоне.

Последовательно повторить тест на частотах: `1000`, `2000`, `4000`, `8000 Гц`.

Для каждой частоты:
1. Сгенерировать WAV → PLAY → убедиться в наличии тона.
2. Записать 3 сек → анализ → зафиксировать пик и уровень.

**Критерий успеха:** все 4 частоты обнаружены с допустимым смещением ≤ 25 Гц.

**Критерий неудачи:** любая из 4 частот не обнаружена → не переходить к этапу 3.

### Этап 3. Диапазон 15–17 кГц (переходная зона)

**Цель:** определить, где начинается ослабление верхних частот у динамика и микрофона телефона.

Последовательно повторить тест на частотах: `15000`, `16000`, `17000 Гц`.

**Критерий успеха:** все 3 частоты обнаружены. Roll-off (падение уровня) зафиксирован, но пики видны.

**Примечание:** на этом этапе уровень может быть значительно ниже, чем на 1–8 кГц. Это нормальное поведение большинства динамиков смартфонов. Зафиксируйте уровень для каждой частоты.

### Этап 4. Диапазон 18–19 кГц (целевой профиль BFSK M0)

**Цель:** определить, поддерживает ли конкретное устройство рабочий диапазон SilentNetwork.

Последовательно повторить тест на частотах: `18000`, `18500`, `19000 Гц`.

**Критерий успеха:** все 3 частоты обнаружены, доля энергии 18–19 кГц > 50%.

**Критерий неудачи:** частоты 18–19 кГц не обнаружены в записи. Это **валидный результат**, означающий, что конкретное устройство физически не поддерживает профиль M0.

> [!NOTE]
> FAIL на этапе 4 не означает ошибку в коде. Это характеристика аппаратуры.
> Запишите модель устройства, версию Android, фактический AudioSource и результат.

## 6. Сценарии сквозного тестирования «Телефон ↔ Компьютер»

Все команды ПК выполняются из каталога `C:\Projects\SilentNetwork\acoustic-lab`.

### Сценарий 1: ТЕЛЕФОН → КОМПЬЮТЕР (Проверка динамика телефона + микрофон ПК)

**Подготовка ПК:**
1. Проверить устройства:
   ```powershell
   python calibrate.py --list-devices
   ```
2. Определить индекс входного устройства (микрофон), записать в протокол.

**Тест:**
1. Разместите телефон на расстоянии **0.5 м** от микрофона компьютера.
2. На компьютере запустите запись фона (без воспроизведения):
   ```powershell
   python scanner.py --capture 10 --device <INPUT_INDEX> --out results/sn014-android/ambient.wav
   ```
3. Начните запись микрофоном ПК:
   ```powershell
   python scanner.py --capture 5 --device <INPUT_INDEX> --out results/sn014-android/phone_to_pc_18500hz.wav
   ```
4. **Сразу после запуска** на телефоне: частота `18500 Гц`, длительность `3 сек`, нажать `PLAY`.
5. По завершении записи — анализ на ПК:
   ```powershell
   python analyze.py results/sn014-android/phone_to_pc_18500hz.wav --json results/sn014-android/phone_to_pc_18500hz.json --plot results/sn014-android/phone_to_pc_18500hz.png
   ```

**Ожидаемый результат:**
- Чёткий пик на 18 500 Гц (±50 Гц) в спектре.
- Уровень пика выше фонового шума минимум на 10 dB.
- Отсутствие сильных паразитных гармоник в слышимом диапазоне (< 16 кГц).

### Сценарий 2: КОМПЬЮТЕР → ТЕЛЕФОН (Проверка динамика ПК + микрофон телефона)

Это целевой сценарий SN-015. Стимул создаёт и воспроизводит **Windows
Desktop Acoustic Lab** (commit `f497f66`), запись выполняет Android Audio Lab
Receiver. Сетевой транспорт не используется.

**Подготовка ПК** (каталог `acoustic-lab`):

1. Установить зависимости и запустить приложение:
   ```powershell
   python -m pip install -r requirements.txt
   run_desktop.bat
   ```
2. Приложение открывается в безопасном режиме: звук не воспроизводится без
   явного флага. Полный сценарий с физическим PLAY:
   ```powershell
   run_desktop.bat --hardware-test
   ```
   Без `--hardware-test` кнопка PLAY не выполняет физическое воспроизведение.
3. Проверить окружение без звука:
   ```powershell
   python desktop_app.py --smoke-test
   ```

**Тест:**

1. В Windows Desktop Lab выбрать частоту (`18500 Гц` для профиля M0),
   длительность тона и выходное устройство. Сгенерировать стимул. WAV стимула
   сохраняется вместе с JSON параметров `*.tone-*.json`.
2. Записать **Test ID**, показанный Desktop Lab, и ту же ожидаемую частоту в
   Android Audio Lab.
3. На телефоне в разделе **B. LAPTOP → PHONE RECEIVER**:
   - вставить Test ID с Windows;
   - выбрать ту же ожидаемую частоту;
   - выбрать длительность записи (рекомендуется `10 сек`);
   - нажать **«НАЧАТЬ ЗАПИСЬ»**.
4. Сразу после перехода в состояние `RECORDING` нажать **PLAY** в Windows
   Desktop Lab. Факт воспроизведения фиксируется в playback JSON
   (`playback.performed = true`). Если PLAY не выполнялся, Windows JSON
   содержит `playback.performed = false`, и тест не считается выполненным.
5. После окончания записи на телефоне нажать **«Передать в анализатор»**,
   затем **«Экспорт записи WAV»** (`sn015_<test_id>_rx.wav`) и
   **«Экспорт JSON-отчёта»** (`sn015_<test_id>_result.json`).
6. Скопировать WAV и JSON с телефона на ПК через USB-кабель.
7. Импортировать WAV телефона в Windows Desktop Lab. Windows создаёт
   собственный `*.analysis.json`. Android JSON пока не импортируется GUI; его
   проверяют по контракту
   [`SN-015-RESULT-FORMAT.md`](../../../docs/hardware-calibration/SN-015-RESULT-FORMAT.md)
   и сверяют `wav_sha256` с фактическим WAV.

**Ожидаемый результат:**

- Микрофон смартфона зарегистрировал ожидаемую частоту (для `18500 Гц`
  допуск ±50 Гц на этом этапе).
- `detected_frequency_hz` в Android JSON близок к `expected_frequency_hz`;
  `frequency_error_hz` согласован с разностью.
- Бортовой анализатор телефона и Windows-анализ дают согласованные значения
  частоты пика, RMS и клиппинга.
- `wav_sha256` в Android JSON совпадает с SHA-256 переданного WAV.

> [!IMPORTANT]
> Совпадение частоты — измерение, а не PASS модема. Передача данных, BER/PER,
> дальность и «неслышимость» этим сценарием не проверяются.

### Сценарий 3: Сетка частот (полная характеризация тракта телефона)

**Обязательная последовательность** (см. раздел 5):

| Этап | Частоты, Гц | Цель |
|---:|---|---|
| 1 | 1000 | Контрольный тон |
| 2 | 1000, 2000, 4000, 8000 | Слышимый диапазон |
| 3 | 15000, 16000, 17000 | Переходная зона |
| 4 | 18000, 18500, 19000 | Целевой профиль M0 |

Повторите для каждой частоты тест «Телефон → ПК» (сценарий 1) и зафиксируйте
уровень пика, шумовой пол и наличие гармоник. Это позволит построить
относительную АЧХ динамика телефона.

## 7. Что передать Agent 1 по итогам испытаний

Для детального анализа в Acoustic Lab передайте Agent 1:
1. Записанные WAV-файлы: `sn015_<test_id>_rx.wav` (телефон) и
   `phone_to_pc_*.wav` (ПК).
2. JSON-отчёты `sn015_<test_id>_result.json` и Windows `*.analysis.json` /
   `*.playback-*.json` одного и того же `test_id`.
3. Модель смартфона, версию Android, фактический sample rate, запрошенный и
